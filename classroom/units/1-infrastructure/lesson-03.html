Lesson 1.3: Docker Networking

INTERMEDIATE

📚 What You Are Learning

One concept: How Docker containers communicate with each other and the outside world using networks.

You'll learn about bridge networks, custom networks, and why containers should NOT use the default bridge.

✅ You Should Already Have

  • Docker Compose working (from Lesson 1.2)
  • At least one running container you can test with
  • Basic understanding of IP addresses and ports

📖 New Words

  • Bridge Network — Docker's default network type that acts like a virtual switch
  • Service Name Resolution — Containers can talk to each other using service names instead of IP addresses
  • Network Isolation — Containers on different networks cannot communicate
  • network_mode — Special mode where a container shares another container's network stack

🔧 Lab Steps: Create a Custom Network

List Current Networks

docker network ls

You'll see default networks: bridge, host, none

Create a Custom Bridge Network

docker network create homelab-net

This creates a new network that containers can join.

docker network ls

You should now see homelab-net in the list.

Create a Test Compose Stack with Custom Network

Create a new directory and docker-compose.yml:

mkdir -p ~/homelab/network-test
cd ~/homelab/network-test

File content:

version: "3.8"

networks:
  homelab-net:
    external: true

services:
  web1:
    image: nginx:alpine
    container_name: web1
    networks:
      - homelab-net
    ports:
      - "8091:80"

  web2:
    image: nginx:alpine
    container_name: web2
    networks:
      - homelab-net
    ports:
      - "8092:80"

Start the Stack

docker compose up -d

Both containers are now on the homelab-net network.

Test Container-to-Container Communication

Connect to web1 and ping web2 by service name:

docker exec -it web1 ping -c 3 web2

You should see successful ping replies!

Try the reverse:

docker exec -it web2 ping -c 3 web1

This proves service name resolution works on custom networks.

Test HTTP Communication Between Containers

Install curl in web1 and make a request to web2:

docker exec -it web1 apk add curl
docker exec -it web1 curl http://web2:80

You should see the nginx welcome HTML!

Inspect the Network

docker network inspect homelab-net

Look for the "Containers" section — you'll see web1 and web2 with their IP addresses on this network.

📚 Why Custom Networks Matter

❌ Default Bridge Problems:

  • Containers can only talk via IP addresses (no service name resolution)
  • Legacy mode, not recommended for production
  • Less isolation and control

✅ Custom Bridge Benefits:

  • Service name DNS: Containers resolve each other by service name
  • Better isolation: Only containers on the same network can communicate
  • Easy management: You can have multiple networks for different stacks

🔒 Network Isolation Example:

If you create two networks (arr-net and homeassistant-net), containers on arr-net CANNOT talk to containers on homeassistant-net unless explicitly bridged.

🚀 Advanced: network_mode for VPN Routing

When you use Gluetun (VPN container) with qBittorrent, you want qBittorrent's traffic to go through Gluetun's VPN tunnel.

Solution: Use network_mode: service:gluetun

version: "3.8"

services:
  gluetun:
    image: qmcgaw/gluetun
    container_name: gluetun
    cap_add:
      - NET_ADMIN
    environment:
      - VPN_SERVICE_PROVIDER=your-provider
      - VPN_TYPE=openvpn
    ports:
      - "8080:8080"  # qBittorrent web UI exposed via Gluetun

  qbittorrent:
    image: linuxserver/qbittorrent
    container_name: qbittorrent
    network_mode: service:gluetun  # ← Shares Gluetun's network!
    environment:
      - PUID=1000
      - PGID=1000
    volumes:
      - ./config:/config
      - ./downloads:/downloads

Result: All qBittorrent traffic goes through Gluetun's VPN. If the VPN drops, qBittorrent has no internet.

You'll implement this in Unit 2 when setting up downloaders.

🔧 Troubleshooting Decision Tree

Problem: Containers cannot ping each other by name

→ Make sure both containers are on the SAME custom network
→ Service name resolution does NOT work on the default bridge
→ Check: docker network inspect NETWORK-NAME

Problem: "network not found"

→ Create the network first: docker network create homelab-net
→ If using external: true in compose, the network must exist before docker compose up
→ Alternative: remove external: true and let Compose create it

Problem: "network already exists"

→ That's OK! You can reuse existing networks
→ If in docker-compose.yml, use external: true to reference the existing network

Problem: qBittorrent web UI not accessible with network_mode: service:gluetun

→ Port mappings must go on the Gluetun service, not qBittorrent
→ Example: Gluetun has ports: ["8080:8080"] to expose qBittorrent's web UI
→ Access at Gluetun's IP, not qBittorrent's (qBittorrent has no separate network)
